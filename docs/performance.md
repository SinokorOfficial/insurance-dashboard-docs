# 성능

레코드 약 6,150건을 브라우저가 통째로 받아 그리는 구조라, 병목이 **서버가 아니라 클라이언트**에 있습니다.

## 무엇이 느렸나

`render()` 한 번은 **필터 후 남은 행 전부**를 `innerHTML` 로 다시 만듭니다(통계·차트까지 재계산).
실제 브라우저 측정:

| 남은 행 | 렌더 1회 |
|---|---|
| 6,146 (조건 없음) | **4,332 ms** |
| 4,881 (`a` 검색) | **6,152 ms** |
| 3,130 (`s` 검색) | 2,374 ms |
| 175 (`sinokor` 검색) | 128 ms |

그런데 이걸 **두 곳에서 과하게 부르고 있었습니다.**

1. 기동할 때 **조건 없이** 한 번 → 6,146행 전부
2. 검색창의 `input` 이벤트마다 → **글자 하나 칠 때마다**

13글자를 치면 13회 반복하며 누적 5,877행을 처리했습니다. 앞 두세 글자에서 이미 수 초간 멈춥니다.

## 조치 ① 검색은 Enter / [검색] 버튼에서만

```
예전: render() 13회 · 누적 5,877행
지금: render()  1회 ·        4행     → 처리량 1/1,469
```

- 검색창을 비우면(✕) 전체로 되돌립니다 — 한 번만 일어나므로 부담 없습니다.
- **칩 필터는 클릭이라 즉시 반영**합니다(타이핑이 아니라 괜찮습니다).

## 조치 ② 조건이 없으면 아무것도 그리지 않는다

첫 화면은 표·통계·차트를 비우고 안내만 띄웁니다.
조건(칩·검색어·현시점)을 걸거나 **[전체 보기]** 를 누를 때부터 보여줍니다.

```
전송 완료 후 화면 준비
  개선 전   6,146행   4,332 ms
  개선 후       0행     116 ms      37배
```

!!! danger "게이트는 렌더가 아니라 '보이는 행' 함수에 걸어야 합니다"
    엑셀·CSV 내보내기가 같은 함수를 쓰므로, 렌더만 막으면 **화면은 비었는데 내보내기는 전체**가 됩니다.
    화면과 내보내기가 어긋나면 안 된다는 규칙은 [과거 버그](screens.md#_5)에서 나온 것입니다.

## 조치 ③ 화면이 쓰는 필드만 보낸다

레코드를 통째로 HTML에 박아 보내는데, 표가 그리는 컬럼은 16개뿐이었습니다.

```
레코드 JSON   8.19 MB → 5.14 MB   (37% 감소)
```

가장 컸던 `원본목록`은 서버가 이미 가공해 함께 보내던 **순수 중복**이었습니다.
자세한 목록은 [데이터 모델](data-model.md#_5).

## 조치 ④ 선박 조회 — 파일을 매번 다시 읽던 것

| | 전 | 후 |
|---|---|---|
| 보험자 교차조회 (로컬) | 888 ms | **1.9 ms** |
| 선명 코드표 조회 | 11.5 ms | 캐시 |
| 못 찾는 경우 | 19.1 ms | **0.39 ms** |
| 외부 API 호출 | 매번 새 연결 | **연결 재사용, 40~55%↓** |

## 남은 것

- **렌더 1회 비용은 그대로**입니다. `[전체 보기]` 는 약 1초(콜드 4.3초) 걸립니다.
  표시 행 수 제한이나 가상 스크롤이 필요하지만 화면 동작이 바뀌므로 담당자 확인 사항입니다.

## 측정에 관한 교훈

!!! danger "직접 만든 소켓 코드로 HTTP 지연을 재지 마세요"
    이 프로젝트에서 **같은 사안을 두 번 오진**했습니다.

    **① "인증서에 OCSP가 없다"** → 있었습니다.
    인증서 확장을 **영어 이름**으로 걸러서, 한국어 Windows의 실제 표기와 맞지 않아
    애초에 매칭될 수 없었습니다. → **확장은 이름이 아니라 OID로 찾으세요.**

    **② "요청당 2초 서버 지연"** → 없었습니다.
    `SslStream` + `StreamReader.ReadLine()` 으로 keep-alive 요청을 반복 측정했더니
    요청당 1.7~2.4초가 나왔는데, 리더가 버퍼를 채우려고 다음 데이터를 기다려 막힌 것이었습니다.
    `curl` 로 다시 재니 **요청당 5~7ms** 였습니다.

    → HTTP 지연은 **`curl -w`** 로 재세요(`time_appconnect` / `time_starttransfer` / `num_connects`).
    그리고 반드시 **대조군을 같은 방식으로 함께** 재세요.

!!! danger "테스트 프로세스를 확실히 정리하세요"
    개발 서버를 여러 번 띄우고 셸 명령으로 죽였다고 생각했는데 **실제로는 안 죽어서**,
    Windows에서 여러 프로세스가 같은 포트에 동시에 바인딩됐습니다. 요청이 인스턴스마다
    흩어져 들어가며 11~55초의 가짜 지연이 나왔습니다.

    → 측정 전에 **프로세스 수를 먼저 확인**하세요.
